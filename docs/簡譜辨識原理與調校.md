# 簡譜幾何分析 v2：原理與調校

## 一、初版為什麼辨識不出來

1.0.0 初版把整頁圖丟給 Tesseract 辨識一次，實測有三個致命問題：

| 現象 | 根本原因 |
| --- | --- |
| 「1 5 1 5」讀成「SS SS」 | 數字與中文歌詞共用同一個模型，中文模型不擅長讀單獨數字 |
| 高低音（數字上下的小圓點）**全部遺失** | Tesseract 只回報字元，**不會回報附加符號** |
| 節拍快慢（減時線）**全部遺失** | 同上；八分、十六分音符因此全變四分音符 |

第三點是無法用「換參數」解決的：延音線、減時線、高低音點、附點
在 Tesseract 的字元模型裡根本沒有對應的輸出類別。

## 二、v2 的做法：版面自己量，只把數字交給 OCR

```
灰階圖
  └─ Otsu 自適應門檻 → 墨跡遮罩
       └─ 橫向投影 → 分列（core band）
            ├─ 圓點／減時線的矮投影列 → 掛回所屬數字列（satellite）
            └─ 欄投影 → 字團（cluster）
                 └─ 8-連通元件分析
                      ├─ 面積最大者 → 主字形
                      │    ├─ 細寬且位於字高中段 → 延音線 `-`
                      │    ├─ 瘦高            → 小節線 `|`
                      │    └─ 其餘            → 數字 → Tesseract（--psm 10 + 白名單）
                      └─ 其餘小元件 → 附加符號，依相對位置判定
                           ├─ 基線之上的圓點 → 高八度 `'`（可疊兩層 `''`）
                           ├─ 基線之下的圓點 → 低八度 `,`
                           ├─ 基線之下的細橫線 → 減時線 `_`（可疊 `__`）
                           └─ 右側同高的圓點 → 附點 `.`
```

## 三、開發過程中踩到的三個真實陷阱

### 1. `ImageOps.autocontrast` 會把 JPEG 振鈴雜訊拉成墨跡

同一張圖，墨跡像素量：

| 前處理 | 墨跡像素 | 辨識結果 |
| --- | --- | --- |
| 原始 JPEG（僅 Otsu） | 21,117 | 完全正確 |
| autocontrast(cutoff=1) | 37,000+ | 產生大量假圓點 |
| autocontrast + 固定門檻二值化 | 45,368 | 幾乎全錯 |

白底樂譜的動態範圍本來就滿了，autocontrast 只會放大壓縮雜訊。
**因此 `ocrMode = jianpu2` 時完全跳過 autocontrast**，改用 3×3 中值濾波去除孤立雜點。

### 2. 用 `band.bottom` 當基線會被小節線帶歪

小節線高達 46 px，把整列的 bottom 從 272 撐到 288。
於是位在 y=279 的減時線被判定成「列內的橫線」→ 誤讀成延音線。

**修正**：基線與字高改由「已判定為數字的元件」取中位數求得
（`Metrics.base`、`Metrics.dh`），與小節線、延音線無關。
這一項修正讓標準答案測試從 36 分之 13 直接跳到 **36/36**。

### 3. 漢字歌詞列不能只靠幾何特徵判斷

漢字的筆畫常是分離的：有些瘦高像小節線、有些細寬像減時線。
實測「星光落在窗前」被切成 17 個主字形、誤產出 4 個假小節。
量測過的幾何特徵都不夠決定性：

| 列 | 內容 | 字團寬/字高 | 主字形/字團 | 垂直堆疊比例 |
| --- | --- | --- | --- | --- |
| 音符列 | `1 5' 1, -` … | 0.62–0.66 | 0.93 | 0.00 |
| 歌詞列 A | 漢字 | 0.94 | 4.00 | 0.75 |
| 歌詞列 B | 漢字 | **0.60** | 1.89 | **0.11** |
| 歌詞列 C | 漢字 | 0.91 | 2.86 | 0.14 |

歌詞列 B 的寬高比與堆疊比例都落在音符列的範圍內。

**最終判準**：直接用中文模型讀一次，看回傳字串裡**有沒有真的漢字**
（`looks_like_lyrics()`）。這是唯一可靠的判準。
未安裝中文語言包時才退回幾何備援（`text_score` 或 `comps_per_cluster`）。

## 四、可調參數

全部位於 `app/omr/jianpu.py` 頂部，**單位都是「字高的倍數」，與 dpi 無關**：

| 參數 | 預設 | 意義 | 何時要調 |
| --- | --- | --- | --- |
| `MIN_GLYPH_AREA_REL` | 0.010 | 主字形最小面積 | 掃描雜點多 → 調大 |
| `DOT_MAX_REL` | 0.42 | 圓點尺寸上限 | 高低音點沒抓到 → 調大 |
| `DOT_MIN_AREA` | 3 | 圓點最小像素數 | 低 dpi 掃描 → 調小 |
| `DASH_MIN_ASPECT` | 2.2 | 延音線細長程度 | 延音線被當數字 → 調小 |
| `DASH_MAX_H_REL` | 0.34 | 延音線最大厚度 | 手寫粗線 → 調大 |
| `BAR_MIN_ASPECT` | 2.2 | 小節線瘦高程度 | 小節線漏抓 → 調小 |
| `UNDERLINE_MIN_ASPECT` | 2.0 | 減時線細長程度 | 減時線漏抓 → 調小 |
| `DIGIT_MIN_H_REL` | 0.55 | 數字高度下限 | 數字被當雜點 → 調小 |
| `TEXT_WIDTH_RATIO` | 0.80 | 幾何備援：判為漢字的寬高比 | 僅無中文模型時生效 |
| `TEXT_COMPS_PER_CLUSTER` | 1.35 | 幾何備援：判為漢字的筆畫密度 | 僅無中文模型時生效 |

## 六、效能

每個數字一次 Tesseract 呼叫（約 74 ms）。實測一頁約 3–12 秒，視音符密度而定。
三頁樂譜約 35 秒。

## 七、顯示層：標準簡譜排版

`web/assets/jianpu-render.js` 把內部 ASCII 速記排版成**標準簡譜寫法**。
內部之所以不直接存標準寫法，是因為「數字下方的點」與「跨音符的共用底線」
無法用單純字元序列表示，存 ASCII 速記才好編輯、好比對、好寫進檔案。

| 內部速記 | 標準簡譜寫法 | 實作方式 |
| --- | --- | --- |
| `5'` `5''` | 數字上方一／兩點，兩點垂直疊放 | flex 直向排列的圓形 `<i>`，固定高度保證整列對齊 |
| `5,` `5,,` | 數字下方一／兩點 | 同上，且外距預留該列最深減時線的空間 |
| `5_` `5__` `5___` | 數字下方一／二／三條減時線 | `::after` 畫第一條，`box-shadow` 疊出第二、三條 |
| 相鄰音符都有減時線 | **連成一條共用底線** | 底線畫在含左右內距的容器上，相鄰容器的線自然相接 |
| `5.` | 數字右側小圓點 | `.jp-aug`，略高於基線 |
| `-` | 數字右側增時線 | 全形 `－`，與數字同高 |

依據：[中文維基百科—簡譜](https://zh.wikipedia.org/zh-tw/%E7%B0%A1%E8%AD%9C)（「在上方垂直加上兩點」）、
[Numbered musical notation](https://en.wikipedia.org/wiki/Numbered_musical_notation)
（「Where there is more than one dot above or below the number, the dots are vertically stacked」）、
[pickd—簡譜與數字譜怎麼看](https://pickd.tw/how-to-read-numbered-notation/)（共用底線＝一拍內連奏）、
[字母簡譜網](http://www.c-hz.net/index/article/info?cid=12&id=130)（附點在右側、增時線加一拍）。

**編輯流程**：畫布預設顯示標準簡譜；點一下音符欄（或用 `Alt`＋方向鍵跳進去）
切成 ASCII 速記輸入框，失焦後立刻重新排版。貼上的全形字元會自動正規化
（`＿`→`_`、`－`→`-`、`，`→`,`、`。`→`.`、`｜`→`|`、全形數字→半角）。
無法解析的 token 會以紅色虛線底標示並**原樣保留**，不會被猜成別的音符。

## 八、v2.1：高低音點完全讀不到的根因

使用者回報「重裝後仍然沒有任何高低音標示，歌詞也出現大量亂碼」。
用一張**點密集、解析度較低**的測試譜重現後，發現兩個層級的同一類錯誤：

### 8.1 列切分被圓點自己綁架（主因）

`find_bands` 原本用**所有投影列的中位數高度**當核心列門檻。
問題是一行音符會產生 1～2 條高低音點列，**點列的數量往往多於真正的內容列**，
中位數因此塌到圓點的高度（約 5px），門檻變成 2.5px，於是點列自己升格成「核心列」。

後果有兩個，剛好對應使用者看到的兩個症狀：

- 高低音點不再被當成鄰近數字列的附屬符號，永遠接不回數字上 → **一個八度記號都不會出現**。
- 點列與減時線列被當成內容列送進中文模型，Tesseract 對著一堆橫線圓點硬湊出漢字
  → 出現「人人人人還雪有」「上二二」這類亂碼歌詞列。

修正：門檻改用**墨水量加權**的中位數。一列 8 個圓點的墨水量只有數字列的幾十分之一，
加權後基準必定落在真正的內容列。

### 8.2 字高估算被圓點拉低（次因）

`_metrics` 的候選集包含了圓點（圓點寬高比接近 1，通得過原本的形狀篩選）。
數字與圓點數量接近時，高度中位數會落在兩者之間，圓點就通得過「主字形」門檻，
被當成數字送去 OCR ——同時製造出多餘的音符、又少掉八度記號。

修正：先用**上四分位高度**定出數字的尺度，再只取高度 ≥ 該尺度 60% 的元件算中位數。

### 8.3 修正後實測

| 測試 | 結果 |
| --- | --- |
| 點密集測試譜（12 音、12 個八度記號） | token 12/12 全對，信心值 0.97 |
| 模擬真實版面（3 行音符＋3 行中文歌詞） | 音符 24/24 token 全對；歌詞逐字 22/24（92%） |
| 原標準答案測試 | token 36/36、附加符號 23/23，無回歸 |
| 6 個內建樣本 | 全部 `done`；三頁 PDF 37.5 秒（約 12.5 秒／頁） |

## 九、歌詞前處理：量測推翻了直覺

原本打算對歌詞列加「放大＋自動對比＋二值化」，這是 OCR 的常見套路。
實際用中文語言包量測逐字命中率後發現**反而變差**：

| 前處理 | 17px 小字 | 22px 中字 |
| --- | --- | --- |
| 原尺寸 | **96%** | **92%** |
| 放大到 44px | 62% | 92% |
| 放大＋自動對比 | 62% | 92% |
| 放大＋二值化 | 62% | 92% |
| 放大＋二值化＋留白 | 62% | 88% |

LANCZOS 放大會讓筆畫變糊，`tessdata_fast` 對此特別敏感。
**所以不要對歌詞做二值化或大倍率放大。**

但另一組測試又顯示沒有單一選擇穩定勝出：某些列原尺寸整列讀不到（0/8），
放大版卻全對；某些列放大版會在寬字距的空隙裡吐出 `“` 這類憑空標點，原尺寸較乾淨。

因此 `_lyric_ocr` 的做法是**兩種都讀，用「漢字數優先、信心值次之」挑選**，
再用 `_clean_lyric` 濾掉「不含漢字、只有一個字元、且是標點」的 token。
歌詞列數不多，多一次辨識的成本可以接受。

## 十、診斷工具

辨識不對時不要憑猜測調參數，先跑：

```
python tools/debug_page.py 你的樂譜.pdf --page 1
```

會在 `build/debug/` 產生標註圖與文字報告，標出每一列的範圍、量到的字高與基線、
每個字形的分類（數字／增時線／小節線／圓點／減時線），以及最終輸出。
上面 8.1 的根因就是靠這張圖一眼看出來的。

## 十一、v2.2：我自己造成的回歸，與判準的加強

### 11.1 放大倍率上限寫錯，把放大整個關掉了

v2.1 為了避免「很矮的列被放大成兩萬像素寬」而加了上限：

```python
scale = min(scale, 4, max(1, 4000 // max(1, strip.width)) or 1)   # 錯的
```

`4000 // strip.width` 拿頁面寬度去除，**頁寬只要超過 2000px 就算出 1**，
等於把整個放大路徑關掉。而先前已經量過：不放大時有些歌詞列會整列讀不到（0/8）。
使用者回報「歌詞比上一版還低」就是這個。

**為什麼測試沒抓到**：當時的測試圖只有 1240px 寬，`4000 // 1240 = 3`，
剛好和原本算出的倍率一樣，測試全過。真實掃描件都在 2400px 以上。

修正是改看**放大後的寬度**：

```python
scale = min(scale, 6)
while scale > 1 and strip.width * scale > MAX_STRIP_WIDTH:   # 12000
    scale -= 1
```

教訓已寫進 `tools/test_regression.py`：測試圖的尺寸必須涵蓋真實掃描件的尺寸，
只用小圖測會漏掉與尺寸相關的錯誤。

### 11.2 中文模型會對著數字硬湊漢字

在 2480px 寬的測試譜上，一列 8 個數字被 chi_tra 讀成
「說 1 說 史 說 2 DD 6」——漢字占 44%，通過了原本「≥40% 漢字」的門檻，
**整列音符被當成歌詞丟掉**。

所以判準改成中文模型 + 幾何否決權：

1. 幾何若**強烈**顯示是等寬單字元（`text_score < 0.75` 且 `comps_per_cluster < 1.20`），
   直接判定音符列，不理中文模型 —— 漢字不可能又這麼窄又這麼單純。
2. 否則才看中文模型，且漢字占比門檻從 40% 提高到 **60%**。
   真正的歌詞列實測是 100% 漢字，44% 只會出現在誤讀。

### 11.3 浮水印過濾

曲譜網站的譜常有「僅供個人學習使用,歡迎轉載、分享、收藏,篡改必究!」這類頁尾，
它會被當成歌詞列，再被切成一個字一個小節塞進譜裡。

`_is_watermark` 的判準刻意設嚴：**要命中兩個以上版權關鍵詞，或含網址**。
關鍵詞清單也刻意**不放**「分享」「收藏」「所有」「轉載」——
第一版放了，結果「所有的星光都收藏起來」被判成浮水印。
誤刪使用者的歌詞比漏刪浮水印嚴重得多。
